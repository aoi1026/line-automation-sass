# 運用ガイド

日々の運用と、困ったときの確認手順をまとめています。

## デモモードと本番モードの違い

店舗の **Channel Access Token が未設定の間はデモモード**で動作します。

| | デモモード | 本番モード |
| --- | --- | --- |
| 条件 | LINEチャネル未設定 | Channel Access Token 設定済み |
| メッセージ | **実際には送信されない** | LINEに実送信される |
| メッセージ履歴 | チャネル欄が「デモ」で記録 | チャネル欄が「LINE」で記録 |
| 用途 | 導入前の動作確認・研修 | 通常運用 |

デモモードでも予約・顧客・自動配信・分析のすべての機能が動くため、
LINE公式アカウントを用意する前に運用フローを試せます。

## 自動配信が送られないときのチェックリスト

上から順に確認してください。

1. **自動配信設定が有効か** — 管理画面 → 自動配信設定 で該当の種別がオンになっているか
2. **お客様がLINE連携済みか** — 顧客詳細のLINE欄が「連携済み」か。未連携の場合、メッセージ履歴に「スキップ」として記録されます
3. **テンプレートが有効か** — 管理画面 → テンプレート で該当種別のテンプレートが有効か（無効な場合は標準文面が使われます）
4. **配信エンジンが動いているか** — 外部cronが動作しているか。手動確認は次のコマンド:
   ```bash
   curl -fsS "https://<ドメイン>/api/cron/run?secret=<CRON_SECRET>"
   ```
   管理画面 → 自動配信設定 の「今すぐ実行」ボタンでも実行できます
5. **メッセージ履歴の状態を見る** — 管理画面 → メッセージ履歴 でステータスとエラー欄を確認

### 種別ごとの送信条件

| 種別 | 送信されるタイミング | 送られない主な理由 |
| --- | --- | --- |
| 予約確認 | 予約を「確定」で登録した直後 | 未確定（PENDING）で登録した場合は送られません |
| リマインダー | 予約日時の設定時間前 | 既に一度送っている予約には再送しません |
| キャンセル通知 | 予約をキャンセルした時 | — |
| 日時変更通知 | 確定済み予約の**日時を変更**した時 | 料金・メモだけの修正では送りません（意図的な仕様です） |
| 来店お礼 | 「来店済み」にしてから設定時間後 | 来店済みにしていない予約には送られません |
| 再来店リマインド | 前回来店からメニューの推奨間隔が経過 | 今後の予約が入っているお客様には送りません。最終来店から180日以上経過した方も対象外です |
| 誕生日 | 誕生日当日の設定時刻以降 | 誕生日が未登録の場合。年1回のみ |

## メッセージ履歴の見方

**ステータス**

| 表示 | 意味 | 対応 |
| --- | --- | --- |
| 送信済み | 正常に送信された | — |
| スキップ | お客様がLINE未連携のため送らなかった | 連携コードを発行してご案内ください |
| 失敗 | LINE APIがエラーを返した | エラー欄を確認。トークン失効・ブロック等が主因です |

**チャネル**

- **LINE** — 実際にLINEへ送信された
- **デモ** — デモモードのため記録のみ（送信されていない）

## お客様のLINE連携手順

1. お客様にLINE公式アカウントを友だち追加していただく
2. 管理画面 → 顧客詳細 → 「連携コードを発行」で6桁のコードを発行（有効期限24時間）
3. お客様にコードをお伝えし、**LINEのトークにそのまま送信**していただく
4. 自動で連携が完了し、顧客詳細のLINE欄が「連携済み」になります

店頭でのご案内例:

> 「LINEで次回のご予約のご案内やお得なクーポンをお送りしています。
> よろしければ友だち追加のうえ、こちらの6桁の番号をトークに送ってください。」

## 障害時の確認箇所

| 症状 | 確認すること |
| --- | --- |
| 画面が開かない | アプリのプロセスが動いているか、リバースプロキシのエラーログ |
| ログインできない | `SESSION_SECRET` が変更されていないか（変更すると全セッションが無効化されます） |
| データが表示されない | `DATABASE_URL` の接続、PostgreSQLの稼働状況 |
| LINEが届かない | 上記チェックリスト、LINE Developers のチャネル状態、トークンの有効期限 |
| Webhookが動かない | Webhook URLがHTTPSか、「Webhookの利用」がオンか、署名検証エラーがログに出ていないか |
| 短時間で429が返る | レート制限。プロキシが `X-Forwarded-For` を転送しているか確認 |

## 定期メンテナンス

`MessageLog` と `WebhookEvent` は運用とともに増え続けます。
分析は直近のデータで足りるため、古いものは定期的に削除して構いません。

```sql
-- 2年より古いメッセージ履歴を削除
DELETE FROM "MessageLog" WHERE "sentAt" < NOW() - INTERVAL '2 years';

-- 90日より古いWebhookイベントログを削除（デバッグ用途のため短くてよい）
DELETE FROM "WebhookEvent" WHERE "createdAt" < NOW() - INTERVAL '90 days';

-- 使用されないまま期限切れになった連携コードを掃除
UPDATE "Customer" SET "linkCode" = NULL, "linkCodeExpiresAt" = NULL
WHERE "linkCodeExpiresAt" < NOW();
```

> ⚠️ 削除前に必ずバックアップを取得してください（`docs/DEPLOY.md` の「データベースのバックアップ」参照）。

## よくある運用上の質問

**Q. 予約を間違えて「来店済み」にしてしまった**
A. 予約詳細から「確定に戻す」で取り消せます。来店回数・累計利用額も自動で戻ります。

**Q. 過去の予約の内容を修正したい**
A. 来店済みの予約も編集できます（記録訂正のため）。ただしキャンセル済みの予約は編集できません。

**Q. セグメントを削除するとキャンペーンはどうなる？**
A. 未配信（下書き・配信予約済み）のキャンペーンには、削除時点の抽出条件が引き継がれます。
配信対象が「全顧客」に変わってしまうことはありません。

**Q. 同じお客様に同じリマインダーが二重に届くことはある？**
A. ありません。配信済みかどうかはメッセージ履歴で判定しているため、
配信エンジンが何度実行されても重複しません。
